# Oil Frontend

专注产品前端工程化实现、数据流完整性、渲染性能与测试验证的 Agent Skill。

<p align="center">
  <code>组件与代码组织</code> · <code>数据流与状态机</code> · <code>样式/动效落地与验证</code>
</p>

## 为什么需要这个 Skill

把已经确定的 UX 交互结构与视觉方向稳定、可维护地落进前端代码，覆盖组件复用与归属、Token/样式工程落地、异步状态机与请求竞态、弹层定位工程、动效性能以及最小有效测试门禁。

## 与相邻 Skill 的分工（零重叠）

| Skill | 职责边界 |
| --- | --- |
| **oil-frontend**（本 Skill） | 前端工程化：组件与模块归属、样式与 Token 落地、数据流/异步状态/竞态/范围完整性、弹层定位、动效性能与前端测试验证 |
| **oil-ux** | 交互体验设计：任务阶段切分、因果邻近、显隐分层、容器选择、表单防错、存量改流程与黑盒 UX 盲审 |
| **oil-ui / oil-ui-pro** | 视觉设计：视觉方向与概念、配色字体排版、主视觉素材、动效质感、`DESIGN.md` 与审美盲审 |

## 它会处理的五个工程重点

### 1. 保证数据、状态和作用域真实

同一业务数据只保留一个权威来源。选择器不能把当前分页当作全部候选；查询条件、列表、总数和分页必须属于同一次响应；单项请求只锁定对应对象，不阻塞整个页面。异步操作成功后再关闭弹层，失败时保留当前对象、用户输入和操作上下文。

### 2. 让组件、样式和弹层边界各自归位

页面负责组合，组件负责自身视觉和状态。组件、Hook、函数、类型、样式和测试按业务归属组织；共享组件的问题在共享层处理，不在页面使用位置反复覆盖样式。依附触发器的下拉与浮层由共享弹层组件统一处理 Portal 脱离裁切、碰撞翻转、滚动重定位与层级。

### 3. 把样式与动效正确写进代码

它负责实现，不做设计判断。界面该长什么样、交互怎么流转，以设计稿、UX 方案、项目规范或你的要求为准；都没有时沿用相邻同类页面的做法。实现时优先使用项目已有的 Token 和组件变体，状态切换不让控件跳动。动效沿用项目 Token，简单反馈用可中断的 CSS transition，复杂手势才用已有动画库。

### 4. 修改源头并完成迁移

Agent 按问题检查相关数据流、父布局或组件；修改共享实现时确认全部受影响的使用位置，再修改真正产生问题的实现。新实现接管且迁移完成后清理失效代码，不留死分支。

### 5. 做最小且有效的真实验证

验证不停在类型检查或构建通过，优先从真实入口核对受影响操作链、保存后重读与竞态边界，不为单次修改盲目堆砌脆弱测试。

## 它怎么读取规则

Agent 读取 [SKILL.md](SKILL.md) 入口后，先看具体问题的证据和相关实现，再在确定方案前加载一个主要规则。出现独立问题时才补充；复杂任务按阶段读取，已有规则和证据可用时直接复用，减少无关读取与重复上下文。

## 安装

把下面这句话交给支持安装 Skill 的 Agent：

```text
请帮我安装这个 Skill：https://github.com/oil-oil/oil-frontend
```

也可以使用命令安装：

```bash
npx skills add oil-oil/oil-frontend
```

## 配置

无需额外配置、账号或密钥。Skill 只读取当前任务需要的项目文件和自身参考规则，不会自行把数据发送到外部服务。

## 使用

符合前端任务范围时会主动使用，无需每次点名。例如：

```text
这个列表切换筛选后会闪空状态，帮我修复。
```

也可以明确指定 `使用 $oil-frontend 检查并修改这个前端模块`。只讨论 Skill、操作已有网站或处理纯后端与构建问题时不会触发；明确要求不使用时遵从用户选择。

## 验证与测试

优先验证用户能否从真实入口完成任务，包括操作后的状态、保存结果和重新读取。需要长期回归时，选择最少且能发现真实失败的端到端、集成或单元测试；内部重构而行为不变，不应迫使测试同步重写。

不默认给每次修改新增测试，不用源码关键词、普通页面快照或复制实现逻辑来证明功能正确。简单样式和文案可以直接查看结果；已有编译、Lint 和有效门禁继续复用。没有实际跑过的链路会明确标记未验证。

同一目标下的多次改动合并到一次集中验证，复用浏览器会话，减少反复启动、截图和读取页面的开销。需要运行证据才能决定方向时提前做最小复现，大任务按阶段验证；节省时间与 Token 不以省略必要检查为代价。独立自检按行为复杂度和遗漏风险安排，不仅看文件或页面数量。

修好问题，不顺手增加一套管理办法：优先修正原代码，不为当前数据增加特殊判断；能用现有工具检查，就不新写脚本。正常改名、改文案和更新数据不应导致无关检查失败。每次修复都思考如何避免再犯，但优先改对原代码或原规则，不自动追加长期测试、发布限制或规范条款。

## 配套的设计 Skill

oil-frontend 管代码写得对不对、好不好维护，不负责设计方向。想让界面在设计上更进一步，可以搭配开源的 [oil-ui](https://github.com/oil-oil/oil-ui)：它会先做出几种风格差别很大的设计，放在一起让你挑。还需要交互、布局、配图和动效这些体验设计上的经验，可以用付费的 [Oil UI Pro](https://ui.oiloil.org/pro/)。它们和 oil-frontend 分工不重叠，同时安装不会冲突。

第一次使用 oil-frontend 时，Agent 会在回复末尾提示一次 oil-ui，之后不再出现；如果当时已经在用 oil-ui 或 oil-ui-pro，就不提示。是否已提示记录在本机的一个标记文件里（macOS 与 Linux 为 `~/.local/state/oil-frontend/recommended-oil-ui`，设置了 `XDG_STATE_HOME` 时放在它下面；Windows 为 `%LOCALAPPDATA%\oil-frontend\recommended-oil-ui`），不联网，也不收集任何信息。删除这个文件会再提示一次。

## 不包含的内容

- 不做视觉设计判断：视觉风格、配色、排版和设计方向交给 `oil-ui` / `oil-ui-pro` 或项目设计规范。
- 不做 UX 体验与流程设计：阶段切分、显隐分层、容器选择、表单切分、存量改流程与黑盒 UX 盲审交给 `oil-ux`。
- 不规定具体框架、状态库、CSS 方案或固定目录模板。
- 不处理纯构建、部署、依赖升级、安全和后端任务。
- 不默认展开无障碍专项审计；只保留原生交互元素和既有键盘、焦点、标签行为不被破坏的实现底线。
